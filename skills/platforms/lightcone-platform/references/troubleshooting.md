# Lightcone 发布问题处理与证据表

来源：2026-10-27“更新 lightcone 部署配置”聊天中多实验发布、用户纠正与处理记录。下表不复制生产标识、审批链接、Webhook 或原始数据；最后一轮滚动验收在采集时仍进行中，不记录为整体成功。

| 问题 / 曾出现的误判 | 正确处理 | 完成证据 / 禁止推断 |
| --- | --- | --- |
| 标题已显示，但表单模型/KFC 暂时空白 | 等待目标配置响应业务成功，核对返回值与页面；失败或超时保持未知 | 曾经重载后模型非空，确认是页面就绪判断错误；不能称模型缺失 |
| puregpu 或零实例被直接跳过 | 检查具体模型与发布记录，分类依据是事实而非架构名称 | Caster app/link、zone、实例数可支持已发布；0/0 不否定发布资格 |
| 已发布 GPU 有 flag，CPU 没有，仍补发 | 按该补旗流程的用户规则，GPU 已发布目标值就整实验跳过，CPU 暂不补齐 | 需线上已发布版本证据，草稿有值不算已发布 |
| 未发布草稿夹带旧变更 | 保存 diff 与发布 diff 分别核对，列出额外变化 | 不擅自恢复，不顺带发布 |
| 重复发布单被“驳回”后立即重试 | 查询是否退回申请人且仍审批中，待负责人结束旧流程 | 旧单终态、平台不再阻塞；不能代批或终止他人单据 |
| 缺少模型判断错误后撤销新增 flag | 先解决数据加载和发布证据矛盾，不根据未知值改写草稿 | 真正需要清理本次草稿时记录前后值和适用授权，不能覆盖别人修改 |
| diff 图片实际为普通配置页 | 等待正确弹窗，查看图片确认内容与实验；错图补正 | 记录前/后方向；文本检查和图片检查互补 |
| 用单个低点报“持续下降 23%” | 检查同口径完整时序及最新恢复，区分时点变化与窗口统计 | 附 query、rate 窗口、样本数和截止时间；不能从均分下降推断模型效果/发布故障 |
| 用户面板与查询数值不同 | 对齐数据源、标签、时间/时区、step、rate interval、聚合与覆盖集合 | 归档数据与补查数据分开；未对齐前不声称逐点一致 |
| 10% 滚动、几十分钟新旧版本共存，却用短时历史均分验收 | 以已更新 pod 同时间窗、同打分头的收敛为主，旧均分只辅助解释 | QPS 更新迹象需与实例/版本状态交叉验证；未确认的 pod 单列 |
| 无 QPS 或无打分一律阻塞 / 一律通过 | 按已授权豁免范围跳过缺失部分，保留有数据部分验收 | 无流量不是效果正常；原来有流量发布后消失必须查因 |
| 多标签页/脚本复制错目标 | 维护服务/实验/页面/发布记录映射，写入和提交前再次核对 | 禁止只替换实验编号而遗留其他服务、cmd、app 或 KFC |

这些处理规则不授权自动发送外部通知或处理审批。需要通知时，沿用当前任务明确授权的接收方和内容范围；错误结论应向同一已授权接收方发送更正，不扩大发送范围。
