# 应用监控验收与通知

## 有效样本与版本归属

建立逐 Pod 记录：平台发布版本、实际镜像 tag、启动时间、首次观察 Healthy/up 时间、升级后有效打分恢复时间、最后样本时间。原地升级沿用旧 Pod 名称，不能通过名称后缀或历史发布号分新旧组。分页或筛选未覆盖全部实例时明确覆盖缺口。

新版本验收只纳入升级完成且健康接流后的样本；counter/rate 等窗口必须全部在升级/恢复之后。窗口不明时核对面板实际查询定义，不机械等待固定分钟数。重启期间历史末值、面板 Last 非空、跨边界 rate、缓存数据都不能证明新版本打分正常。重启后有效样本尚缺失时标为“待恢复/未验证”。

同时记录两组同时间窗同打分头的有效 Pod 数、缺失/无效/零值、均值、min/max、离散程度、版本间偏差及持续时间。新旧流量分布不同，不要求不同请求的平均分浮点精确相等；这不是同请求逐条一致性的证明。用户无阈值时报告真实偏差和持续趋势，不编造 SLA。整体平均不能掩盖异常 Pod 分群；无流量也不能报效果正常。

全量完成后已无旧版本同时接流时，保留滚动期间新旧对照证据，再验证全体新版本 Pod 收敛；不要将已停止上报的旧时序当作当前对照。

## 监控入口与口径

**首选直接用 PromQL 范围查询采集，不要求先打开 Moni/Grafana。** 查询能力只负责返回原始时序，本场景负责版本分组、窗口过滤、统计比较和发布决策。当前环境提供 `davinci-tool:promql` 时，先读该技能并使用其 Hawkeye 查询脚本；技能不可用时使用环境中已配置且获授权的 Prometheus 查询工具，不硬编码其他机器的路径或凭据。

建立本次监控定义：`source_id`、app/环境/集群标签、Pod 标识标签、指标及 PromQL、单位、打分头（适用时）、range 窗口、start/end、step、允许的数据延迟及判定标准。source_id 沿用本会话用户已确认值；缺失时按查询工具规则确认，不猜测、不从其他任务复制。Lightcone server_id、Grafana datasource UID 与 Hawkeye source_id 不是同一种标识，不能直接互换。

适用指标从用户提供的查询、应用维护的监控定义或已确认的指标文档获取。定义已齐备时直接查询；定义不明时才用面板 query/Inspect 或应用文档发现口径。面板是口径参考，不是必经采集入口。只读查询失败或空结果要区分权限、数据源、标签、指标改名及无流量，不以失败结果判分数为0或发布通过。

| 应用 | 监控选择 |
| --- | --- |
| Qserver / ad-rank 场景 | QPS、错误/延迟，以及按打分头和 Pod 的有效均分、无效分比例；使用本应用实际指标 |
| davinci-model-server 等其他 Caster app | 应用约定的请求量、错误率、延迟和业务指标；只有提供打分指标及定义时才做打分验收 |

每项指标独立确认数据源和适用标签，不假设业务与容器指标使用同一 source。按实际 Pod 标签查询全部目标和对照，核对返回标签、覆盖数与 Caster 实例表；不凭命名推测 CPU/GPU cmd 与 app 一一对应。Prometheus 查询结果的 Pod 名称只用于关联实例，镜像与启动时间仍来自 Caster。

Qserver 已观察到的指标包括 `galaxy_server_score`、`galaxy_server_score_count`、`galaxy_server_invalid_score`，以及按头使用的 `galaxy_server_score_seperate`（实际拼写）。有效均分可涉及 rate 和1000000缩放，按头还涉及 name 标签；这些是发现线索，不是适用于所有 app 的通用表达式。使用核实的完整表达式，不任意更改分母、标签聚合顺序、缩放、rate窗口，也不将请求加权均分误写成 Pod 均值。除数为0、NaN/Inf、缺点都单列，不静默过滤成“正常”。

经已安装查询技能执行的调用形态（路径按实际安装位置解析；变量均为本次已确认值）：

```bash
python3 "$PROMQL_SCRIPT" range --source "$SOURCE_ID" \
  --query "$PROMQL" --start "$START_UNIX" --end "$END_UNIX" --step "$STEP_SECONDS"
```

保存精确表达式、查询参数、原始带时间戳 JSON 以及分析结果。前后基线和新旧同期使用相同语义、标签与时间对齐；同一轮公共 end 固定，不能每查一个 Pod 就移动终点。

### 窗口与完整性

沿用用户观察窗口；未另行指定时，本发布场景采用2min观察窗口，并在每个纳入样本时刻要求 Pod 已启动至少5min且已确认健康接流。完整2min验收要求窗口起点也满足条件，不把末点满5min误作整窗成熟；指标 rate/lookback 更长或接流更晚时按实际边界延后。

若已知数据末点存在修订，使用本次明确记录的延迟（本案例为latest减2min），并记录状态采集时间和样本时间。延迟不能证明历史永不修订。摘要 N/A/未接流与表格 healthy/up 冲突时不以旧表或有分代替当前接流证明。

基线覆盖所有待升级 Pod。实际运行镜像分组：真正旧镜像、此前已目标镜像的保留实例、本次重启/更新实例。已目标镜像首批的前后比较只能说明重启影响，真正旧镜像 Pod 仍需检查升级前后；缩容移除的时序和跨重启旧值不作为当前旧版本对照。无旧版本同时接流时，改为全量目标版本内部统计和已存基线比较，明确证据边界。

## 阶段、定时及最终报告

用户要求定时报送时保存频率和本次范围；本案例约定每5分钟及阶段结束报告，最终另发完整报告。用可用的线程定时能力持续跟踪，避免重复发布/重复通知；完成后停止定时任务。

报告最小字段：

- 目标、旧新镜像、当前阶段和截止时间（明确时区）。
- 平台状态、目标/已升级/更新中/未升级数量，健康与接流状态。
- 新版本升级后有效样本窗口与 Pod 覆盖，旧版本同期覆盖；缺失项单列。
- 同窗各头打分范围、均值/偏差、无效打分和持续性；明确是监控统计一致还是同请求回放一致。
- 结论：继续观察、当前阶段无持续异常、部分验证或具体异常；下一步及停止点。

每份阶段/定时/最终报告都附可复核的 Caster 发布单链接。

最终报告分别给出平台发布终态、实例镜像生效、升级后打分验收，附真实截图/发布单/原始数据的本地证据索引，不把其中一项成功等同整体成功。

## 企微通知

外部通知仅在用户明确授权收件目标与范围后发送。群 Webhook 与会话机器人 CLI 是不同接口；使用本次用户提供的目标，不复用历史 key。把密钥保存在仓库外的受限文件或安全配置中，不打印、不提交、不嵌入公开技能或定时任务提示。

按授权补发部署开始，随后发送中间、阶段及最终报告；补发标注实际事件时间。消息使用完整可审查结论，排除未经升级后样本证明的“正常”。记录发送时间、报告文件和回执，只有业务 errcode=0 才记为发送成功；失败如实报告，结果未知时不要盲目重复。截图只发送真实网页证据，必要时分图；不要把渲染 JSON 的差异图作为发布截图。

消息按渠道实际大小上限拆分；企业微信群 Markdown 通常按4096字节限制检查，不能按字符数代替UTF-8字节数。以报告标识/文件与回执防重，不为历史漏发伪造当时已送达。最终报告成功发送后停止对应自动化，不停止其他任务监测。
