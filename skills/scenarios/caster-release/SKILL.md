# Caster 镜像发布（第二层）

读取 [Caster界面](../../platforms/caster-platform/SKILL.md)。从 Lightcone 进入时再读 [Lightcone界面](../../platforms/lightcone-platform/SKILL.md)。仅把 Lightcone 当导航入口属于本场景；需要同时修改两平台时才转联合场景。

实证边界：2026-10-27 已完成迭代发布表单、预检、无需审核、确认发布、首批健康与升级后打分对比，并执行继续所有；全量滚动当时尚在进行。不能把本案例写成全量成功，不能推定审批必然豁免。

## 输入与边界

沿用本会话明确的应用、环境/zone、镜像、时间、并发及批次要求。缺项先只读核实，不复制历史任务授权。用户要求发布即执行真实发布和验证；只准备方案则不提交。其他任务的暂停状态独立保留。

浏览器遵循当前环境的浏览器技能，使用本 chat 自己的空间。发现他人修改目标配置、未知差异或冲突流程，停止该目标写入并上报，不覆盖或合并。没有授权不重试、回滚或调整并发。

## Workflow

1. **定位和基线**：核对 Lightcone 服务/实验的 CPU 或 GPU app，点击对应 Caster 链接。待异步数据就绪，核对生产/测试环境、zone、实例数、旧镜像和在途流程。目标版本已运行时避免重复发布。记录旧版本、健康状态、打分基线及当前配置证据。
2. **填写表单**：迭代发布 → 生产环境提醒 → 继续。等待应用、实例数及当前镜像真实加载，再填写用户要求的部署策略、滚动策略、tag、并发度、回滚方案。仅镜像升级时不附带生效新应用配置、不修改资源/flags/副作用 Webhook。示例参数为滚动、同起同停、目标 tag、并发1、文本“默认方案”；不是所有任务的默认值。
3. **预检和审批**：检查字段读回及允许差异，保存真实完整截图。发起流程后可能先出现预检，预检正常再发起。记录本次流程与时间，等待真实审批；“无需审核”可进入确认发布，不代审批人操作。
4. **确认及首批**：点击确认发布，核对本次发布单详情中的镜像/策略/并发、旧新配置 Diff。若 init 尚未更新，使用继续 → 继续批次启动首批。创建单或确认按钮成功不等于 Pod 已升级。
5. **首批验收**：通过实例表的目标镜像、启动时间、Running/healthy/up 判断升级和接流；原地升级不按 Pod 名称中的发布号分类。按 [升级后打分验收与通知](references/monitoring-reporting.md) 验证新旧 Pod。观察倒计时禁用继续时等待，不绕过门禁。
6. **后续推进**：用户要求首批正常后“继续所有”时，在平台允许继续后直接执行，不反复请求许可；保留并发度。正在更新时不为切换选项暂停任务。否则按已授权批次策略推进。继续批次可能仅推进一个并发批次，不能当成整个30%阶段完成。
7. **完成或停止**：跟踪平台实际终态，核对目标实例全部目标镜像、健康及接流，等待升级后指标恢复再验收。持续异常、超时、未知状态或他人修改时停止后续动作并报告；不自动回滚。分别记录平台发布、实例版本生效、监控验收，证据不全写部分验证。
