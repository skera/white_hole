# Lightcone + Caster 发布 bin（第二层，待实证）

读取两项依赖：[lightcone-platform](../../platforms/lightcone-platform/SKILL.md)、[caster-platform](../../platforms/caster-platform/SKILL.md)。只使用第一层已核实的平台动作；不得将 Lightcone 的“新配置发布”假定为 bin 发布。

## 执行前确定映射与时序

从用户上下文、实际页面或正式文档确认：
- Lightcone 服务/实验/环境与 Caster 应用/环境/集群的对应关系。
- bin 的准确版本/制品来源、目标实例及平台实际提供的摘要或版本标识。
- 哪个平台持有制品、哪个更新版本引用、哪个实际触发部署；动作是否会自动影响另一平台。
- 两平台动作的先后依赖、每一步成功的证据，以及 CPU/GPU 或新旧版本共存期间的兼容要求。
- 发布前基线、发布后业务验收、观察窗口和失败时的处理范围。

未确认的顺序列为未知，不默认“先 Caster 后 Lightcone”或相反。缺失信息影响后续动作时，继续独立只读检查并询问最小关键问题；不能跳过第二层改用第一层直接发布。

## 编排

1. 两个平台分别读取当前状态、版本和待发布差异，建立目标映射及允许变更集合。
2. 根据已确认依赖形成动作表：平台、动作、输入版本、前置条件、预期结果、验证方式、失败后停止点。平台间依赖由本层管理；不要求第一层相互调用。
3. 保存发布前版本与配置证据，核对是否有其他进行中发布或未授权差异。bin 升级不自动授权附带修改 flags、组包大小或部署资源。
4. 如果仅要求准备方案，输出动作表后结束。包含发布授权且实际路径与前提齐备时，按动作表执行；前一步结果通过验证后，才进入依赖它的下一步。自动联动已触发的动作不能重复提交。
5. 两平台对应的本次任务都完成后，核对最终配置/版本与实际运行实例的关联，再进行部署后监控；不能用一个平台成功替代整体成功。
6. 任一阶段失败、状态不明或出现持续异常时停止依赖它的后续动作，明确哪些平台已改变、哪些未执行。不要为“保持一致”擅自回滚或继续发布。

## 输出与边界

提供两平台目标映射、制品版本、实际采用的顺序及依据、各步任务/时间/结果、最终版本与实例覆盖、业务监控和残留差异。无实际发布案例前标为“待实证”；发现已可执行但未执行时标为“方案已准备”；部分完成时逐平台报告，不能简写为“发布成功”。
