# Lightcone 发布配置（第二层）

首先读取依赖 [lightcone-platform](../../platforms/lightcone-platform/SKILL.md)。UI 操作、状态语义及监控公式以平台层为准，不在场景中重定义。

## 输入

取得 Lightcone 入口、服务/实验集合、环境、两侧目标参数（名称/类型/值）、仅保存还是发布、监控 source_id/app/cmd 与验收条件。沿用本次已确认的范围和授权，不重复询问；不要因列表可见多个实验扩大发布范围。

## 编排

1. 调用平台读取目标和完整待发布差异，记录变更前状态。发布任务采集约 10 分钟基线或用户指定窗口；若监控不可用，不将之后的部署状态代替监控验收，应先明确缺口如何处理。
2. 建立允许变更集合，例如 CPU/GPU 两侧新增 `download_last_dense_when_no_sparse / bool / true`，及为其必要的“配置galaxy”开关。其他配置保持不变。
3. 调用平台编辑、保存并读回，处理重复 flag 或已有不同值的冲突。若任务仅保存，到此报告结果，不触发发布。
4. 调用平台核对完整发布 diff。已有其他待发布变更时暂停该实验，说明旧值 → 新值；仅按用户具体授权处理后重新核对，不沿用历史案例中的恢复授权。
5. 已有发布授权且 diff 通过后，调用平台提交并等待当前发布记录整体完成，验证实例状态。
6. Lightcone 发布及调度部署完成后才开始正式监控验收。调用平台的监控参考，观察各活跃 pod QPS 恢复与每个打分头的稳定性；可先观察约 5 分钟，按采集周期和异常情况延长。
7. 重新读取配置，分别汇总配置持久化、平台部署、监控验收证据。无阈值时报告实际波动，不把历史波动当成功标准。

## 多实验与终止

已明确批量范围时，默认逐实验完成上述流程再继续。持续 QPS 下降、打分异常或发布失败时暂停后续发布并报告；不自动回滚。范围外草稿变更阻塞对应实验，可在授权和风险允许时继续其他独立实验，记录跳过原因。

## 输出

逐实验提供目标变更、必要开关、diff 结论、原有差异及处理依据、保存/发布/部署时间与时区、发布标识、CPU/GPU 实例数、监控覆盖数、source_id/查询/时间窗/步长/rate 窗口、异常与证据路径。结果区分“已保存未发布”“部署失败”“部署完成但监控待确认”“观察范围内验收通过”。未覆盖实例与短时观察限制必须保留。

本场景已有单实验 gflags 发布记录作为依据；不自动证明任意配置字段或所有实验的发布行为相同。
