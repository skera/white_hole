# Lightcone 发布配置（第二层）

首先读取依赖 [lightcone-platform](../../platforms/lightcone-platform/SKILL.md)。第一层仅提供界面栏目和状态语义。执行前读取本层 [操作步骤](references/workflow.md) 和 [问题处理表](references/troubleshooting.md)，需要验收时读取 [监控方法](references/monitoring.md)。这些执行资料均属于第二层。

## 输入

取得 Lightcone 入口、服务/实验集合、环境、两侧目标参数（名称/类型/值）、仅保存还是发布、监控 source_id/app/cmd 与验收条件。沿用本次已确认的范围和授权，不重复询问；不要因列表可见多个实验扩大发布范围。

## Plan 与 Workflow

1. 根据平台界面说明读取目标和完整待发布差异，记录变更前状态。发布任务采集约 10 分钟基线或用户指定窗口；按下方规则分类已有配置、模型证据和监控豁免，不将部署状态代替效果验收。
2. 建立允许变更集合，例如 CPU/GPU 两侧新增 `download_last_dense_when_no_sparse / bool / true`，及为其必要的“配置galaxy”开关。其他配置保持不变。
3. 根据平台界面说明编辑、保存并读回，处理重复 flag 或已有不同值的冲突。若任务仅保存，到此报告结果，不触发发布。
4. 根据平台界面说明核对完整发布 diff。已有其他待发布变更时暂停该实验，说明旧值 → 新值；仅按用户具体授权处理后重新核对，不沿用历史案例中的恢复授权。
5. 已有发布授权且 diff 通过后，根据平台界面说明提交并等待当前发布记录整体完成，验证实例状态。
6. Lightcone 发布及调度部署完成后才开始正式监控验收。按本层监控参考，观察各活跃 pod QPS 恢复与每个打分头的稳定性；先确认实际滚动更新是否结束；约 5 分钟只能作为初始检查，不是最终成功时限。按本层监控参考以已更新 pod 间打分收敛为主，持续观察实际更新周期。
7. 重新读取配置，分别汇总配置持久化、平台部署、监控验收证据。无阈值时报告实际波动，不把历史波动当成功标准。

## 多实验与终止

此补旗流程支持最多同时发布 3 个实验；仅串行授权或用户指定更低上限时遵循较低值。若本次尚未确定并行范围，采用串行。维护“待检查/跳过/已保存/发布中/平台完成待验收/验收完成/豁免/阻塞”的逐实验台账；平台任务完成可释放发布名额，监控观察继续保留，不能把名额释放记为验收成功。提交前计算实际在途发布数，准备草稿和查看截图不占发布名额。持续 QPS 下降、打分异常或发布失败时暂停后续发布并报告；不自动回滚。范围外草稿变更阻塞对应实验，可在授权和风险允许时继续其他独立实验，记录跳过原因。

## 输出

逐实验提供目标变更、必要开关、diff 结论、原有差异及处理依据、保存/发布/部署时间与时区、发布标识、CPU/GPU 实例数、监控覆盖数、source_id/查询/时间窗/步长/rate 窗口、异常与证据路径。结果区分“已保存未发布”“部署失败”“部署完成但监控待确认”“观察范围内验收通过”。未覆盖实例与短时观察限制必须保留。

本场景已有多服务、多实验 gflags 发布与纠错记录；不自动证明任意配置字段或所有实验的发布行为相同。

## 补旗场景的筛选与豁免规则

以下来自原流程后续的用户明确修正，适用于同一目标参数的补齐任务；新任务若明确要求双侧补齐或其他验收条件，遵从新要求。

1. **GPU 已发布目标 flag 且类型/值正确：跳过整个实验，CPU 暂不补齐。** GPU 仅草稿有值时先核实线上版本，不当作已发布；已有不同值按本层操作步骤的冲突规则处理。GPU 未发布目标配置的实验，在授权范围内补齐 CPU/GPU 并发布。
2. **可靠确认没有具体模型时可跳过；字段暂空不等于无模型。** 先完成本层问题处理表的加载、响应和实例/历史证据检查。不能因为 puregpu 类型而跳过，也不能因为 0 pod、0 QPS 撤销本次草稿。
3. **已有发布配置但零实例/无流量：仍可发布配置，缺失效果验证标为豁免。** 此流程用户已允许无 QPS、打分为空时跳过对应效果验证；QPS 有数据就检查 QPS，只有打分缺失就仅豁免打分。新任务未包含该豁免时先明确验收边界，不擅自删减。发布前有流量而发布后突然缺失不适用静态无流量豁免。
4. 无模型、已有 GPU 配置而跳过、零实例但已发布、审批阻塞、监控豁免分别记录；“跳过”和“发布成功”不是同一状态。

## 截图、链接与通知

本次要求通知且接收方已明确时，逐实验提供“服务/实验/模型、真实升级前后 diff 图、对应监控链接”；部署与验收后再提供结论。准备文档本身不授权发消息；不要把历史 Webhook 或账号写入仓库。

- 按本层操作步骤要求验证截图确为目标实验的完整 diff，注明前/后方向。
- 基于当前提供的监控 URL 模板解析并替换 CPU/GPU cmd、app、app regex、环境、实际 KFC/模型和指定数据源，保留模板的重复参数及必要变量。不能仅替换 e 编号或猜测 KFC；未知时标注未核实。
- 关联图、链接、实验和本次发布记录，提交前检查没有跨服务串用。
- 通知发送成功单独验证，不能据此判发布成功。先前错误故障结论应给出修正及最新数据截止时间；不为已撤回的故障判断自动执行回滚。
