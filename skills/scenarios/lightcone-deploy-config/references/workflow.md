# Lightcone 配置发布执行步骤

本参考属于第二层配置发布 workflow。由当前任务给定页面入口、服务、实验、环境、目标配置、授权范围及监控条件；缺少关键目标时不猜测。区分 GPU 实验与该实验内部的 CPU/GPU 部署配置。

## 工具与会话

浏览器优先使用已安装的 ego-browser 技能，先读其当前说明；遇登录/扫码/授权页交还可见浏览器，用户完成后继续。监控使用已安装的 davinci-tool:promql 或现有授权范围查询工具。不要硬编码工具路径、浏览器空间 ID 或旧 ref。UI 重绘后重新定位，注意两侧同名控件。

页面 server_id 不是监控 source_id。app/cmd 标签以当前目标实际配置为准，不从其他实验照搬。工具缺失时报告缺项，不生成虚假的结果。

## 操作与输出

| 动作 | 已实证操作方案 | 返回证据 |
| --- | --- | --- |
| 读取目标 | 服务收藏列表 → 指定服务 → 指定实验 → 配置；核对当前草稿、线上配置、发布状态和两侧实例数 | 目标标识、草稿/线上值、待发布差异、实例数 |
| 编辑 gflags | GPU部署配置 → 配置galaxy → 额外gflags；CPU部署配置按同样目标编辑；核对名称、类型、值与所在侧 | 修改前后值、两侧目标行、必要开关变更 |
| 保存与读回 | 保存 → 保存确认 → 重新读取配置 | 持久化结果；保存成功不代表发布完成 |
| 发布 diff | 新配置发布 → 实际待发布差异确认界面；核对完整线上与草稿差异 | 每项旧值/新值及是否属于场景计划允许的变化 |
| 提交发布 | 已获发布授权且完整 diff 合格后确认；记录当前发布记录标识和时间 | 已触发的本次发布，而不是历史成功记录 |
| 等待部署 | 查看当前发布记录各步骤及整体终态、CPU/GPU 实例数和失败项 | 整体状态、完成时间、未就绪实例 |
| 查询监控 | 按下方引用采集场景计划指定的基线或发布后窗口 | 原始查询、数据源/时间窗、覆盖范围和异常 |

## 写入约束

- 同名 flag 已存在且类型/值一致时不重复添加，区分草稿存在与线上生效。
- “仅新增、禁止修改已有配置”的请求遇已有不同值时报告冲突；明确授权更新时才修改。
- 必要的“配置galaxy”开关必须记录在允许变更集合内，检查它是否引入额外默认值。
- 原有 flags、组包大小、并发度、线程数等不得发生未授权变化；保存后检查完整发布 diff，不能只看新增行。
- 已有范围外差异不得擅自恢复或顺带发布。恢复线上值也是改动草稿；已有具体恢复授权时直接处理并重查 diff，否则列出差异等待决定。
- diff 不完整或无法核对时，不返回“可发布”。保存已成功但发布受阻时，明确报告“已保存未发布”。

## 状态语义

- “更新成功”：保存成功。
- “配置更新触发成功”：已触发发布。
- “配置部署检查中”：未完成。
- 当前发布记录整体“执行成功”：结合实例状态验证完成；中间步骤成功不等于整体成功。

发布按钮消失、QPS 没有下降、配置持久化都不能单独证明实例版本已生效。若配置发布与调度部署分阶段显示，分别记录；失败、超出约定观察窗口或状态不明时停止盲目重试，返回已完成阶段与证据。不得默认重复发布或回滚。

## 监控操作

需要 QPS/打分查询时读取 [监控验收](monitoring.md)。场景计划决定基线、验收时机和阈值；执行结果记录数据、时序新鲜度和实例覆盖。历史建议为发布前约 10 分钟基线、部署完成后约 5 分钟初始观察，均不是固定 SLA。

重新打开配置核对两侧 flag，并分开提供配置持久化、平台部署状态、监控结果。历史案例已覆盖多服务、多实验 gflags 配置发布（含零实例目标），但不代表所有平台能力均已验证。bin 选择、制品校验、与其他平台的映射及先后顺序未实证；遇此类请求先从实际页面或正式文档发现，不将“新配置发布”当作 bin 发布入口。

## 页面就绪、发布资格与阻塞处理

执行配置读取、空值判定、批量发布或截图前，读取 [问题处理与证据表](troubleshooting.md)。

- 页面标题、静态“部署配置”文字或 HTTP 200 不足以证明目标数据加载完成。先确认 URL/服务/实验对应，等待目标配置请求成功且业务状态成功，并核对页面字段与响应一致；只通过当前授权浏览器/工具读取实际发现的接口，不猜测 API 或绕过认证。
- 短暂空白、请求失败、旧实验残留数据均标为“未知”，不得据此删除本次 flag、判定无模型或跳过。空字段需要成功响应与发布/实例证据交叉核对。
- 原场景用户确认：列表同时存在 Caster app/link、zone 和实例数量，是已初始化发布过的证据；`0/0` 只表示当前无实例。此规则作为该平台工作流的已确认经验，不替代本次目标版本的生效验证。
- “无模型”需要可靠加载后的配置和发布证据支持；不按 puregpu 名称、无流量或零实例分类。证据冲突时先查清，不修改草稿来迎合猜测。
- 遇重复发布单，读取关联旧单和实际状态；“驳回到申请人、审批中”仍未结束。不能代批、撤回、废弃他人的旧单；请用户或负责人处理。确认终态及平台锁解除后，重新核对当前 diff 才能重试一次；仍受阻则报告，不循环点击。
- 真实 diff 截图须等弹窗及差异内容加载完毕，检查实验、两侧值和前后方向，长内容分段捕获。普通配置页不能充当 diff 证据；已发布项从对应发布历史取真实差异，不伪造回放。截图错误应更正证据，不重发部署。
