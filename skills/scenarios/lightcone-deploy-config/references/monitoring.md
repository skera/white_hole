# 监控验收

在编辑前取基线，在平台发布检查完成后持续观察实际滚动进度，按 pod 更新状态取验收窗口。这里保留原流程的指标语义；实际使用前核实指标定义及标签。

## 输入与查询模板

替换模板中的 `<APP>`、`<CMD>`、`<ENV>`，使用当前任务确认的数据源。它们是占位符，不可原样查询。不要从服务名称自行猜测 app/cmd 映射。source_id 必须依据当前已确认上下文或实际数据源选择；不能从 Lightcone 的 server_id 推导。

QPS（原流程使用每分钟计数除以 60）：

```promql
avg by (pod_name) (
  galaxy_server_rpc_tt_count{
    app="<APP>", env="<ENV>", cluster=~".*", pod_name=~".*"
  }
) / 60
```

该指标名虽含 count，但不要仅凭名称添加 rate；迁移到其他服务时先核实它是每分钟统计值还是累积 counter。多个集群可能有同名 pod 时应保留 cluster 标签，并相应调整聚合及匹配键。

各 pod、各打分头的平均打分：

```promql
sum by (pod_name, name) (
  rate(galaxy_server_score_seperate{
    cmd="<CMD>", env="<ENV>", cluster=~".*", pod_name=~".*"
  }[2m])
)
/
on (pod_name) group_left
sum by (pod_name) (
  rate(galaxy_server_score_count{
    cmd="<CMD>", env="<ENV>", cluster=~".*", pod_name=~".*"
  }[2m])
)
/ 1000000
```

`seperate` 是实际指标拼写，不要改成 `separate`。直接调用范围查询接口时，将 Grafana 的 `$__rate_interval` 替换为真实窗口；本流程曾使用 `2m` 和 `15s` 查询步长，实际应适配采集周期。rate 窗口横跨部署边界时，最初的结果会混合旧数据；判定稳定性应包含窗口完全位于部署完成之后的数据。

## 数据有效性和覆盖范围

1. 保存原始范围查询结果，记录查询结束时间和每条时序最后一个原始点的时间。
2. 依据采集周期和上报延迟确定新鲜度；历史流程曾用 60 秒作为筛选值，不应机械沿用。
3. 不把“每条时序最后一个值”直接当成当前值；已停止上报的历史 pod 会在范围结果中保留旧值。
4. NaN、Inf、缺失、分母为零和真实零值分别处理。先记录无效点，再对有效点统计，不能过滤后声称全部有效。
5. 分开统计 QPS 和各打分头的覆盖数量；比较监控 pod 集合与平台实例集合，注明指标覆盖 CPU、GPU 还是其中一部分。
6. 对新建、退出、短暂中断后恢复的 pod 分别记录。缺失上报不直接等同服务故障，但也不是验收通过。

## 比较方法

- QPS：查看每 pod 的连续时序、最低值、恢复情况和新鲜数据的总量；仅看总量可能掩盖局部异常。启动期间下降可能正常，持续不恢复需报告。
- 打分：分别比较每个 `name`（如 cvr、ctcvr），查看有效性、跳变及相对发布前基线的偏移。
- 比较前后尽可能使用同一 pod 集合和相同统计口径；实例更替时同时报告集合变化。总 QPS 与每 pod 平均 QPS 不可混用。
- 可报告 `(after / before - 1) * 100%`；before 为零或缺失时不计算百分比。
- pod 等权平均打分是描述统计，不等于按请求量加权的全服务平均打分。报告时标明口径。
- 用户有阈值时按阈值验收；无阈值时报告实际波动和观察窗口，不把某次百分比波动固化成通用成功标准。

平台实例全部就绪，但只有部分 pod 上报时，应写“平台部署成功；监控覆盖 N 个活跃 pod，其余未验证”。持续异常时暂停后续实验，提供异常时间、pod、打分头、数据缺口与发布阶段；回滚须依据本次授权范围处理。

## 来源与适用边界

源自 2026-10-27 聊天“更新 lightcone 部署配置”的多实验记录及用户对滚动更新验收的纠正。最新一轮部分监控仍进行中，不视为全部完成。

公开版本参数化了内部地址、服务标识、数据源实例及 pod 信息，没有复制原始监控数据、认证配置或私有工具源码。本 skill 固化的是操作与验收流程，不预先证明目标 flag 的业务效果，也不携带访问 Lightcone/监控系统的授权。


## 滚动更新：优先验证同一时刻的 pod 间收敛

用户明确说明该发布采用约 10% 并发滚动，可能持续几十分钟；模型更新过程中新旧版本打分会不同。该比例和时间是本案例条件，其他任务先读取实际策略，不能硬编码为平台常量。

1. 平台发布检查成功之后继续跟踪实例滚动；不能按“成功后 5 分钟”截断为最终验收。
2. 每个 pod 记录版本/部署状态、QPS 变化与恢复时间、最后有效样本时间。QPS 低谷/中断是更新迹象，不单独证明版本更新；缺少版本证据时标为“更新状态待确认”。
3. 分开已更新、更新中、待更新及状态未知的 pod。对已确认更新且流量恢复的 pod，使用同一时间窗、同一 name 的有效打分观察是否收敛；对整体结论保留尚未更新/未知/缺失 pod 的数量。
4. 报告每打分头的 pod 数、均值、min/max、离散情况与持续时长；不同请求分布的 pod 不要求浮点精确相等。无明确阈值时不把某次 1%–4% 离散率固化为 SLA；“一致”指在可比流量和指定观察标准下收敛，无持续异常分群。
5. 版本切换中出现双峰或先降后升，先看是否随滚动收敛；有流量 pod 持续分群、更新后 QPS 不恢复或无效值持续，才报告具体异常与证据。收敛后又开始一轮变更，重新标记该轮，不沿用上轮完成结论。
6. 历史基线用于上下文与 QPS 恢复辅助判断，不能替代 pod 间验收。历史请求平均分降低不等于模型质量降低，更不能直接归因于本次 flag。未发布对照实验也同步变化时，应说明共同变化、保留因果不确定性。

## 报告前的数据复核

- 将单点差值、窗口均值变化、完整趋势和当前状态分开；提供准确截止时间，不把旧低点描述成当前持续下降。
- 用户面板与本地查询有分歧时，核对 query、数据源、cmd/app、时区、窗口、step、实际 Grafana rate interval、聚合方式及 pod 集合。`[2m]` 是旧案例选择，不等于面板实际窗口。
- 保留当时归档与最新补查两份记录，不混合来源。若滚动/审批等待期间基线已过时，实际提交前补取基线并记录时间；不能把提交前发生的变化归到本次发布。
- 请求平均分仅是监控统计；对故障或回滚建议先给出持续趋势、版本状态和覆盖证据。纠错时撤回不成立的故障结论，不仅修改百分比。

## 无流量与部分指标缺失

依据场景传入的授权豁免执行：发布前已为零实例且无 QPS/打分时可省略效果验证，结论写“配置发布完成，效果验证豁免（无流量）”，而非“效果正常”。有 QPS 无打分则验证 QPS 并标记打分豁免/未验证。原来上报、发布后突然为空时，先查更新中断、标签变化或异常，不能自动套用豁免。
