# 监控验收

在编辑前取基线，在平台部署完成后取验收窗口。这里保留原流程的指标语义；实际使用前核实指标定义及标签。

## 输入与查询模板

替换模板中的 `<APP>`、`<CMD>`、`<ENV>`，使用当前任务确认的数据源。它们是占位符，不可原样查询。不要从服务名称自行猜测 app/cmd 映射。source_id 必须依据当前已确认上下文或实际数据源选择；不能从 Lightcone 的 server_id 推导。

QPS（原流程使用每分钟计数除以 60）：

```promql
avg by (pod_name) (
  galaxy_server_rpc_tt_count{
    app="<APP>", env="<ENV>", cluster=~".*", pod_name=~".*"
  }
) / 60
```

该指标名虽含 count，但不要仅凭名称添加 rate；迁移到其他服务时先核实它是每分钟统计值还是累积 counter。多个集群可能有同名 pod 时应保留 cluster 标签，并相应调整聚合及匹配键。

各 pod、各打分头的平均打分：

```promql
sum by (pod_name, name) (
  rate(galaxy_server_score_seperate{
    cmd="<CMD>", env="<ENV>", cluster=~".*", pod_name=~".*"
  }[2m])
)
/
on (pod_name) group_left
sum by (pod_name) (
  rate(galaxy_server_score_count{
    cmd="<CMD>", env="<ENV>", cluster=~".*", pod_name=~".*"
  }[2m])
)
/ 1000000
```

`seperate` 是实际指标拼写，不要改成 `separate`。直接调用范围查询接口时，将 Grafana 的 `$__rate_interval` 替换为真实窗口；本流程曾使用 `2m` 和 `15s` 查询步长，实际应适配采集周期。rate 窗口横跨部署边界时，最初的结果会混合旧数据；判定稳定性应包含窗口完全位于部署完成之后的数据。

## 数据有效性和覆盖范围

1. 保存原始范围查询结果，记录查询结束时间和每条时序最后一个原始点的时间。
2. 依据采集周期和上报延迟确定新鲜度；历史流程曾用 60 秒作为筛选值，不应机械沿用。
3. 不把“每条时序最后一个值”直接当成当前值；已停止上报的历史 pod 会在范围结果中保留旧值。
4. NaN、Inf、缺失、分母为零和真实零值分别处理。先记录无效点，再对有效点统计，不能过滤后声称全部有效。
5. 分开统计 QPS 和各打分头的覆盖数量；比较监控 pod 集合与平台实例集合，注明指标覆盖 CPU、GPU 还是其中一部分。
6. 对新建、退出、短暂中断后恢复的 pod 分别记录。缺失上报不直接等同服务故障，但也不是验收通过。

## 比较方法

- QPS：查看每 pod 的连续时序、最低值、恢复情况和新鲜数据的总量；仅看总量可能掩盖局部异常。启动期间下降可能正常，持续不恢复需报告。
- 打分：分别比较每个 `name`（如 cvr、ctcvr），查看有效性、跳变及相对发布前基线的偏移。
- 比较前后尽可能使用同一 pod 集合和相同统计口径；实例更替时同时报告集合变化。总 QPS 与每 pod 平均 QPS 不可混用。
- 可报告 `(after / before - 1) * 100%`；before 为零或缺失时不计算百分比。
- pod 等权平均打分是描述统计，不等于按请求量加权的全服务平均打分。报告时标明口径。
- 用户有阈值时按阈值验收；无阈值时报告实际波动和观察窗口，不把某次百分比波动固化成通用成功标准。

平台实例全部就绪，但只有部分 pod 上报时，应写“平台部署成功；监控覆盖 N 个活跃 pod，其余未验证”。持续异常时暂停后续实验，提供异常时间、pod、打分头、数据缺口与发布阶段；回滚须依据本次授权范围处理。
