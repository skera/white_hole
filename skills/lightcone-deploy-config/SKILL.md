# Lightcone 部署配置更新

目标：在授权的服务和实验范围内完成“配置修改 → 保存 → diff 核对 → 发布 → 部署完成 → 监控验收”，保证原有配置不被意外修改。

## 输入与准备

从本次请求和已确认的上下文取得：
- Lightcone 页面 URL、服务、实验列表和环境；区分“GPU 实验”与该实验内部的 CPU/GPU 部署配置。
- 目标 gflags 的名称、类型、值，以及需修改的 CPU/GPU 两侧。
- 是仅保存配置，还是包含发布；已有明确发布授权时不重复询问。
- 监控 source_id、app/cmd 标签、观察窗口及用户指定的验收阈值。

缺少会影响目标或实现的字段时才询问。页面 URL 的 server_id 不是监控 source_id；不同实验的 app/cmd 也不能直接复用。不要因页面列出多个实验就扩大发布范围。

浏览器操作优先使用目标环境已有的 ego-browser 技能，并先读取其当前说明；监控可使用已安装的 davinci-tool:promql 技能或环境已有的授权 Prometheus 范围查询工具。不要硬编码技能安装路径、浏览器空间 ID 或元素 ref。缺少工具时说明具体缺项，不能编造查询结果。

遇到登录/扫码/授权页，交还可见浏览器给用户完成认证，确认后继续。不要读取或复制登录凭据。

## 1. 检查现状并记录基线

逐个实验操作，记录实验标识、线上版本、当前草稿、发布状态、CPU/GPU 实例数和当前目标 flag。
- 已有目标 flag 且类型和值相同：不重复添加；检查它在线上还是仅在草稿。
- 目标 flag 已存在但值或类型不同：若需求仅为“新增且禁止修改已有配置”，停止该项并说明冲突；只有本次明确授权更新时才修改。
- 当前草稿与线上存在其他差异：记录并在发布前解决范围问题，不能默认覆盖或顺带发布。

获取发布前监控基线，建议覆盖约 10 分钟；确认所选标签确实返回目标服务数据。监控语句与判定方法见 [监控验收](references/monitoring.md)。基线只作对照，不证明新配置生效。

## 2. 修改和保存

从服务收藏列表进入目标服务，再进入目标实验的“配置”。
1. 在“GPU部署配置”定位“配置galaxy”和“额外gflags”。
2. 如新增 flag 需要开启“配置galaxy”，将开关变更作为此次明确记录的必要变更；开关可能带来的其他默认值仍须逐项检查。
3. 添加名称、类型和值；例如 `download_last_dense_when_no_sparse / bool / true`。
4. 在“CPU部署配置”按本次范围做同样修改。
5. 核对两侧的新增行及原有配置，点击“保存”并完成保存确认。
6. 重新读取保存后的配置，确认名称、类型和值持久化正确。

每次 UI 重绘后重新定位对应字段。区分 CPU/GPU 区块中同名控件，不复用旧 ref 或仅凭坐标批量填写。

## 3. 发布前的 diff 门禁

打开“新配置发布”的差异确认界面，检查线上配置与实际待发布配置的完整 diff。

允许的变化仅包括：
- 本次授权的 CPU/GPU flag 新增或更新；
- 实现这些变化确实必要且已记录的“配置galaxy”开关；
- 用户另行明确授权处理的既有差异。

逐项核对参数名、类型、值、所在侧；原有 flags、组包大小、并发度、线程数等不得因本次操作发生未授权变化。只有保存成功或看到目标新增行，均不足以通过门禁。

若发现范围外差异：
- 暂停该实验的发布，列出具体旧值 → 新值。
- 不擅自恢复线上值，也不一并发布。恢复草稿同样是修改已有配置。
- 用户已在本次上下文中明确授权恢复时，可直接按授权恢复、保存并再次检查完整 diff。
- 若 UI 无法显示完整差异，不能声称核对完成。

历史案例中曾出现“新增 flags”之外的组包大小差异；只有用户明确授权恢复线上值后，才消除该差异并发布。这不是以后自动恢复组包大小的授权。

## 4. 发布与部署完成确认

本次包含发布授权且 diff 通过后，确认发布，记录时间（包含时区）、实验及发布记录标识。

区分以下状态：
- “更新成功”：配置已保存。
- “配置更新触发成功”：发布已触发。
- “配置部署检查中”：仍在部署。
- 发布记录最终“执行成功”：可结合实例状态判断本次部署是否完成。

等待当前发布记录完成，查看实例数、失败项与异常状态。中间步骤成功、QPS 未下降或发布按钮消失，都不能单独证明全部实例完成。

发布失败、状态不明或观察超出约定窗口时，保留证据，报告阶段并停止继续扩大部署；不要盲目重复点击发布或自动回滚。

## 5. 部署后的监控验收

发布前可以查询基线，发布期间可以辅助观察；正式验收窗口必须在 Lightcone 发布完成并确认调度部署完成后开始。若平台将配置发布与实例调度分开显示，分别记录两阶段时间。

按 [监控验收](references/monitoring.md) 检查每个活跃 pod 的 QPS 恢复与各打分头的稳定性。无用户指定窗口时，可先观察约 5 分钟，结合采集周期、rate 窗口和异常恢复情况延长；这只是初始观察建议，不是固定 SLA。

重新打开配置页面核对两侧 flag，并将配置持久化、平台部署状态和监控结果作为三类独立证据。某一类无法验证时，明确标为未验证。

## 多实验与结果记录

批量范围已明确时，默认逐实验完成修改、diff、发布、验收后再继续。遇到持续 QPS 下降、打分异常或部署失败，暂停后续发布并报告。范围外已有差异只阻塞对应实验；按授权范围和风险决定是否继续其他独立实验，记录跳过原因。

为每个实验记录：
- 目标 flag 与两侧配置、必要开关、原有差异及处理授权。
- diff 核对结果、保存/发布/部署完成时间和最终状态。
- CPU/GPU 实例数、监控覆盖 pod 数、过期/缺失/恢复的时序。
- source_id、实际 PromQL、查询时间窗、步长、rate 窗口、基线和发布后结果。
- 完成、失败、已保存未发布或监控待确认状态，以及证据文件路径。

只报告观测范围内的结论；不能把部分 pod、短时观察或平台“执行成功”描述成全部实例长期稳定。
